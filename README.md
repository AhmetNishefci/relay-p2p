# Relay

A local-first, peer-to-peer field notebook with explicit acknowledgment handoffs.
Built with React Native, Expo, Bare Kit, Corestore, Hyperswarm, and Autopass 3.4.1.

Contributors exchange notes directly and explicitly acknowledge an entry. The
acknowledgment is a separate replicated record: a peer can record it offline, then
the originating device observes it after reconnection. This supports deliberate
field-team handoffs without a central application server. It is not a delivery/read
receipt or proof of human identity. Other Contributors can overwrite shared keys.

Application implementation, tests, artwork and documentation beyond the upstream
template were generated by AI under candidate-directed product decisions. See
[development approach and authentic AI records](docs/AI_USAGE.md).

## Architecture and reliability

React Native owns presentation and interaction; a separate Bare runtime owns Autopass,
Corestore, networking and permission enforcement. Versioned JSON messages cross a
FramedStream pipe with correlated requests, bounded waits and validated payloads.

Notebook and Activity lists use virtualization. Replication invalidations are coalesced
into serialized reads, and explicit refresh callers complete without waiting for a
continuous background stream to drain. Payload budgets and unknown-outcome mutation
recovery have focused regression coverage. See the
[measured results](docs/PHASE7.md) and [native architecture](agent_docs/architecture.md).

## Android setup

Verified on Apple Silicon macOS with ARM64 Android API 36 emulators. iOS is not
verified. This checkout starts from the required official template commit
[`4ad3f8d`](https://github.com/holepunchto/hello-pear-react-native/tree/4ad3f8df5b5f20ce7621c42457795d53b2248c9b).
Original Apache-2.0 [LICENSE](LICENSE) and [NOTICE](NOTICE) are retained.

Install these prerequisites before running commands:

- Node **22.23.3** (`.nvmrc`), npm, and Git. Commands below use **nvm**;
  another version manager is fine if it selects that exact Node version.
- Python 3 for transcript-export tests and integrity checks.
- **JDK 17**. Newer JDKs are not a supported substitute for this template.
- Android Studio / command-line tools, platform-tools, emulator, API **36**, build
  tools, and NDK **27.1.12297006**. Native libraries also use API 34 and NDK
  **27.0.12077973**; Gradle may download these after SDK licenses are accepted.
- An ARM64 AVD on Apple Silicon, or a compatible connected Android device.
  The app minimum is API 29; the checked-in build configuration targets API 36.
- Network access for npm, Gradle/Maven, and initial tool downloads. Peer discovery
  also requires a network that permits the underlying connectivity.

From the repository root, configure your installed tools. These paths are macOS
examples; point `JAVA_HOME` to your actual JDK 17 installation:

```sh
nvm use
node --version                         # v22.23.3
export JAVA_HOME="/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home"
export ANDROID_HOME="$HOME/Library/Android/sdk"
export ANDROID_SDK_ROOT="$ANDROID_HOME"
export PATH="$ANDROID_HOME/platform-tools:$ANDROID_HOME/emulator:$PATH"
java -version                          # 17
npm ci
npx --yes pear@3.0.0 -v                # verified on-demand CLI wrapper
npm run check:upgrade
npm run bundle:bare
emulator -list-avds
```

Start an AVD in another terminal with the same environment:

```sh
emulator -avd YOUR_AVD_NAME -no-snapshot
```

Then confirm it is connected and booted before launching:

```sh
adb devices -l
adb -s YOUR_SERIAL shell getprop sys.boot_completed   # must print 1
npm run android -- --device YOUR_AVD_NAME
```

Use the real AVD name/serial from the commands above. Native projects are generated
by Expo; do not copy another machine's `android/`, `ios/`, or `node_modules/`.
Re-run `npm run bundle:bare` after changing worker code or a worker dependency.

The committed `package.json#upgrade` is a public development project identifier.
It is intentionally reusable for a clean checkout and requires no private signer
for local builds. Do **not** regenerate it for each clone. The original initialization
used `pear touch` and `pear://<key>` as the assessment requires. `check:upgrade`
validates its syntax, not availability of an OTA payload. No deployment is needed.

### Standalone release

```sh
npm run production:android -- --no-bundler --device YOUR_AVD_NAME
```

Stop any debug Metro process. Remove `tcp:8081` reverse forwarding if listed by
`adb -s YOUR_SERIAL reverse --list`, then force-stop and launch the release app.
Release embeds its JavaScript and must run without Metro. The template uses a
local development signing configuration; this is not a production-signed store APK.

The display name, launcher and splash are Relay. The internal package identifier,
`productName` (`HelloPear`), version, and Pear payload paths remain unchanged for
runtime compatibility. The original vector mark and regeneration script are in
[assets](assets/README.md); regenerating assets is not a normal build prerequisite.

## Use Relay

1. On a fresh installation, choose **Create notebook** or **Join notebook**.
2. A Contributor opens **Share**, chooses **Contributor** or **Viewer**, and generates
   an invitation. **Share or copy invitation** opens the native share sheet; choose
   **Copy text** on Android or a trusted app. Possession grants access.
3. On the other device, paste the invitation and join. Keep both apps foregrounded
   and connected. Device labels are optional and unverified.
4. Contributors use **New entry**, save locally, and open an entry to **Acknowledge**.
   Viewers can read entries/acknowledgments but cannot modify them or invite peers.
5. Updates refresh automatically; pull-to-refresh requests another local snapshot.
   Removing an entry requires confirmation and does not promise remote erasure.
6. Open **Notebook activity** for current entry and acknowledgment records. Filter
   **Acknowledgments** or **No acknowledgment**, then tap a row to open its entry.
   Back returns to the same filter. Device-recorded times are not delivery/read
   events; removed entries disappear. This is a current view, not permanent history.

Use independent emulator AVDs or devices with separate application data for a peer
demo. Secondary Android user profiles failed in the pinned Bare runtime and are not
supported by the verified setup. Existing notebooks are never silently replaced.

## DECISIONS

### 1. Sync state

**Problem.** A completed local write and another peer receiving or acting on it are
different events. Autopass updates do not provide per-entry delivery receipts.

**Options.** A single synced badge; connection/update counters; a shared acknowledgment
flag inside the entry; separate acknowledgment records; signed receipt protocols.
The first two overstate available evidence, and embedding a flag couples entry edits
to competing handoffs. Signatures add verification/key-management work and still do
not prove a human read or understood anything.

**Choice and rationale.** Report **Saved on this device** after local completion.
Use separate `ack:<entry-id>:<writer-key>` records for explicit acknowledgment actions.
Bare derives the local key and makes repeats idempotent. UI snapshots distinguish a
local action from observed record claims for other keys. This is useful when teams
want an explicit handoff rather than an inferred transport status.

**Trade-offs.** Users must take an action; there is no global sync badge. These are
mutable claims: another Contributor can overwrite any acknowledgment key. Keys are
not human identities, timestamps do not resolve conflicts, and records bind to entry
IDs rather than content revisions. Removed-entry acknowledgments remain stored but
are hidden from the view. No remote deletion guarantee is made.

**Change the decision when** authenticated per-entry receipt APIs become available,
users need revision-specific acknowledgments, or field evidence shows that explicit
handoffs add more friction than value. Actual replication, duplicate, restart and
cross-writer overwrite tests are described in [handoff semantics](docs/PHASE4.md).

### 2. Pairing and trust

**Problem.** A device holding an invitation can gain access, but the app cannot infer
who the person is or whether their chosen label is truthful.

**Options.** Silent/unrestricted writer admission; read-only invitations without
visible role distinctions; an external account/identity system; explicit capability
sharing with separate Contributor and Viewer behavior.

**Choice and rationale.** Use explicit bearer invitations, explain their power, and
let the inviter choose Contributor or Viewer. Display actual `writable` capability
after admission. Bare rejects Viewer mutations; disabled/absent controls are only
presentation. Participant names and device keys are not verified human identities.

**Trade-offs.** Invitations can be forwarded. There is no owner/admin model, per-entry
ACL, or identity verification. Invitations are shared records: another Contributor
can reuse or cancel them. Autopass selects a locally known invitation for cancellation;
concurrent/stale invitations may remain. Cancellation does not revoke already granted
access or prove other peers observed it.
The API roster may omit the original creator and is not an online indicator.

**Change the decision when** verified identity, finer access control, participant
removal/revocation, or evidence of invitation abuse becomes a real product need.
See [pairing behavior and tests](docs/PHASE3.md).

## Limits and security

- One active notebook per installation. No editor for existing entries or file
  attachments; attachments are optional in the assessment.
- Snapshots are bounded to 200 entries and 1,000 valid acknowledgment records
  (including retained orphans), with a 1,500,000-character normalized budget. JSON
  IPC also has a 4,600,000-byte ceiling that preserves these supported sizes.
  Exceeding limits fails visibly. No pagination yet.
- Peer exchange depends on connectivity and foreground execution. No background
  delivery, fully-synced, verified-person, read-receipt or remote-erasure guarantees.
- An IPC timeout leaves the mutation outcome unknown. No automatic write replay is
  performed. Further entry writes in the current session are blocked until a fresh
  status/snapshot succeeds.
  Use **Review notebook** in the editor (or **Check again**), inspect the result,
  and reconcile before retrying; the draft is retained. A delayed write can still
  complete after refresh. Adds have no exactly-once token.
- Android owner-user ARM64 emulators are verified. Physical devices, iOS, TalkBack
  spoken output, unusual cutouts and three-button navigation remain unverified.
- Pinned tooling has remaining dependency advisories. The audit records their scope;
  do not run a broad `npm audit fix --force` or upgrade prelinked native addons.
