Backend only: no document picker, attachment controls, navigation or native dependency
changes. [AI assistance disclosure](AI_USAGE.md) applies to generated implementation

## Descriptor and storage

Entries retain schema version 1 and optionally contain:

```json
{
  "attachment": {
    "schemaVersion": 1,
    "key": "attachment:<entry-id>:<digest>",
    "filename": "observation.pdf",
    "mimeType": "application/pdf",
    "size": 1048576,
    "digest": "<64 lowercase hexadecimal characters>"
  }
}
```

Allowed MIME labels are `image/jpeg`, `image/png`, `application/pdf`, `text/plain`.
Filenames are trimmed, 1–120 characters, with no path separators/control characters
or `.`/`..`. Size is an exact nonnegative integer, maximum **1,048,576 bytes**. MIME
and filename are labels, not file-format authentication or executable-content checks.
BLAKE2b-256 verifies content against the descriptor, not a human identity or immutable
authorship. Contributors can overwrite shared records, including descriptors/files.

The separate binary record stores association metadata as JSON and bytes in the
Autopass `file` field. The Phase 11A key-range snapshot excludes `attachment:` keys;
normal IPC lists contain metadata only. Files improperly placed under entry/ack
keys can still decode, as documented previously. Retrieval also necessarily decodes
the Autopass file before its size can be checked; it is not a streaming API.

## Protocol and lifecycle

| Operation               | Request                          | Result / behavior                                                                                                  |
| ----------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `attachments.stage`     | filename, mimeType, size, digest | Contributor-only; immutable descriptor binding, worker-generated entryId, opaque handle, input file URI and expiry |
| `entries.addAttachment` | handle, title, body              | Contributor-only; verifies staged bytes, appends binary then entry, returns entry/alreadyRecorded                  |
| `attachments.get`       | entryId                          | Contributor/Viewer; verified metadata, opaque export handle, controlled output URI and expiry                      |
| `attachments.release`   | handle                           | Removes owned temporary files/receipt, without changing replicated data                                            |

Use the existing typed `client.request(op, payload)` API. No request accepts a
filesystem path or contains file contents/base64. File URIs are generated by Bare
under `<notebook>/.attachment-staging/<random-handle>/input.bin` or `output.bin`.
Each Notebook instance owns its handles; another peer or restarted worker cannot
reuse them. Native filesystem access was verified on Android using the already
packaged Expo module. A future picker must copy selected bytes into the reserved
input URI, then submit only the handle/title/body.

- Two live staging slots, at most 64 short-lived receipts. Handles expire after two
  minutes using the local device clock; cleanup runs every 30 seconds and before
  allocation. Active mutations are not swept. Downloads need explicit release after
  use; expiry is a fallback. Background suspension can delay periodic cleanup.
- Startup removes stale random-named slot directories inside the dedicated staging
  root. It never deletes notebook records. Handles are intentionally invalid after
  restart; no persistent client receipt or automatic write replay is implemented.
- Completed-handle duplicates return the original entry without another append.
  A changed/removed entry rejects. Reusing a handle with changed form values does not
  edit the original result. Expired/released handles reject rather than create again.
- Binary and entry appends are not atomic. A failure after either append attempt is
  `ATTACHMENT_UNKNOWN`; possible orphan blobs remain, and that handle cannot replay
  writes. UI integration must retain the reserved entry ID, refresh/reconcile and
  avoid automatic retry. New staging after manual reconciliation is a new operation.
- Removing an entry retains its binary record. No replicated garbage collection,
  physical erasure or access revocation for exported copies is promised.
- Retrieval has an independent one-job lane and an eight-second deadline, preserving
  the existing ten-second client default. Timeout does not cancel storage I/O; the
  lane stays busy until actual settlement. Entry and acknowledgment writes continue.
  Late/shutdown results are not published; local output is cleaned on failure.
- Entry association is rechecked before exporting. A later concurrent deletion does
  not revoke an already-issued URI. Shared writers can replace consistent records;
  digest checking is integrity verification, not authenticated provenance.
- Staging initialization errors disable only attachments (`STAGING_ERROR`), preserving
  existing notebook reads/writes and leaving unsafe/symlinked roots untouched. Core
  Autopass initialization failures still fail closed.
- Cleanup errors are logged; they do not turn a completed save into an apparent
  failure or prevent closing Autopass/Corestore. Temporary residue is retried on startup.

IPC byte/character budgets and notebook quotas are unchanged. No binary payload
crosses JSON IPC. UI rendering and normal Create/Join/Viewer workflows are unchanged.

## Verification

Focused tests cover malformed descriptors/requests, path attempts, the exact 1 MiB
boundary, oversize/digest/size mismatch before append, service ownership, Viewer
writes/retrieval, duplicate handling, expiry, partial-publication orphans, missing/
corrupt association, restart/stale cleanup, concurrent writes, deadline lane retention
and shutdown during a delayed read. Cleanup-failure injection verifies that storage
still closes; that expected logged failure is not an unobserved production error.

The real Node peer test uses three separate persisted Corestores and a local DHT,
not a mocked replication transport. It verifies 1 MiB byte equality, a Viewer joining
after publication, Viewer denials, restart/reconnect with an offline-created entry,
and removal with retained binary data.

Three independent Android debug peers also verified a 1 MiB fixture byte-for-byte
on each device, actual worker Viewer denial, cross-peer handle rejection, duplicate
creation, entry/ack operations and deletion. Original entry and acknowledgment
snapshots were restored (33 entries on each). The first probe ran before all three
inspectors registered and failed before writes; the driver now waits boundedly for
all three. Raw failure and corrected evidence remain separate under ignored
`.assessment-local/phase11b1/`.

Final checks passed all **65 application tests**, four exporter tests, TypeScript,
lint, formatting and Bare bundling. Android debug and standalone release built;
three release peers passed existing CRUD/acknowledgment replication, Viewer UI,
restart persistence and deletion convergence with original 33-entry counts restored.
The final availability guard was also rebuilt into release and cold-launch checked.
A fixed two-second Peer B readiness assertion was too short; PID logs confirmed
actual startup, then bounded readiness polling completed verification. Gradle's
existing deprecation warnings remain. The initial lint gates identified missing
braces; they were corrected without disabling rules or tests.

Reproduce automated checks:

```sh
npm test
npx tsc --noEmit
python3 -m unittest discover -s scripts/tests
npm run bundle:bare
```

With three already-paired debug emulators, the README toolchain and Metro running:

```sh
node scripts/probes/run-attachment-backend.mjs
```

The explicit diagnostic RN entry is never imported by the product and adds no UI
or native module. Generated APKs, logs, fixtures and emulator data stay outside Git.
Android byte verification here uses debug inspection; release has no attachment UI
or production debug hook through which to exercise these new operations.

## Remaining integration

Add document selection/copy, file previews, retrieval/release UI, platform opening/
sharing and accessible error/reconciliation states. Validate actual provider URIs,
permissions, larger fonts and real user-selected formats. File-byte restart/reconnect
is verified by Node peers; equivalent Android attachment-specific interruption tests
remain additional coverage. No physical device or iOS result is claimed.
Staging has bounded files/concurrency, but replicated attachment storage has no
aggregate byte quota, pagination or garbage collection. A future retention policy
needs an explicit distributed design. This phase does not authorize UI work or push.
